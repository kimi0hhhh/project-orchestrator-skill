# 实验数据说明 / EVIDENCE

> 本仓库的设计决策不是拍脑袋：所有关键机制都做过真机对照实验，由独立评审 agent **盲评**打分（评审者不知道产出出自哪个条件）。本文公开全部方法与原始数据，便于复现与质疑。

> All key mechanisms in this repo were tested with controlled runs, blind-judged by an independent reviewer agent. Methods and raw numbers are published here for reproduction and criticism.

## 1. 探针：skill 点名机制 / Probe: skill invocation

同一任务（购物车测试要点），两组 QA 子 agent：

| 组 | 条件 | tokens | 产出 |
|---|---|---|---|
| P1 | 派发 prompt **点名**调用 `test-scenarios` skill | 32.7k | 80 行，12 条用例，每条五段（目标/前置/步骤/预期/证据） |
| P2 | 不点名（契约"推荐 skill"清单两组都在） | 20.0k | 33 行，12 条一行用例 |

**结论**：契约里的"推荐 skill"清单不会自发触发——**必须派发时点名**；skill 加载成本 ≈12k tokens。后续对照实验进一步发现：行数受限（≤60 行）的紧凑工件上点名 skill **反而负收益**（见 §3），因此最终规则是"行数预算 ≥80 行才点名"。

## 2. Demo：参谋链与并行枚举 / Demos: advisor chain & parallel enumeration

- **L1 参谋链（资金提现 PRD）**：单 PM 草稿 → 数据PM+风控合规两个只读参谋 → 返修。参谋产出 21 条挑战（8 BLOCK），抓到单 PM 真实遗漏的监管级红线（收款卡同名校验缺失、余额冻结状态机缺失、反洗钱安排缺失、手续费倒挂）；**挑战吸收率 17/21 = 81%**（阈值 20%），驳回 0。
- **L2 并行枚举（购物车测试计划）**：3 个用例参谋并行穷举 + QA 主笔合并。**每条用例成本与单角色持平（2.7k vs 2.8k tokens/条），覆盖数量翻倍**（26 vs 12 条），参谋间重复仅 1 对。
- **L0（番茄钟 PRD）**：单角色一次过，验证简单任务不加人。

## 3. 对照实验：三条件 × 2 遍，盲评 / Controlled experiment

**方法**：同题 PRD（购物车数量功能，≤60 行），三条件各 2 遍；产出匿名化（X1–X6）后由独立评审 agent 按五维评分卡（0–5×5=30 分）盲评。

| 条件 | 编制 | tokens/遍 | 得分（两遍） | 均分 | 极差 |
|---|---|---|---|---|---|
| C1 基线 | 单 PM，无 skill | 21.1k | 21 / 21 | 21.0 | 0 |
| C2 仅点名 skill | 单 PM + create-prd | 32.3k | 19 / 15.5 | 17.25 | 3.5 |
| C3 本框架 | 草稿 → 2 参谋 → 返修 | 121.9k | 22 / 23 | **22.5** | 1.0 |

**发现**：
1. C3 两遍均前二且最稳；增益集中在**指标口径可测性**（5 分 vs 基线 3 分）与异常边界维度——正是参谋视角瞄准的盲区；
2. **C2（仅点名 skill）两遍均低于基线**：60 行行数限制下 skill 模板挤出实质内容，+11k tokens 买负分；
3. C3 有一例"维度挤出"（四态描述被挑战内容压缩）→ 催生返修回合的维度检查门禁；
4. **诚实声明**：n=2，方向一致但无统计学意义；推广前应 n≥5 + 双评审。

## 4. 端到端对照：小产品双流水线 / End-to-end: mini-product

**任务**：「习惯打卡」单页应用（localStorage、无后端、streak 统计）。两条完整流水线，四类工件（PRD/架构契约/代码/测试计划）匿名化后盲评（40 分制）：

| | B1 传统单角色串行 | B2 本框架 |
|---|---|---|
| 派发数 | 4 | 9 |
| tokens | 163.5k | 357k（2.2×） |
| **盲评总分** | **31/40** | **35/40（+13%）** |
| 分项 | PRD 6 · 架构 7 · 代码 10 · 测试 8 | PRD 8 · 架构 7 · 代码 11 · 测试 9 |

框架赢在：口径精确性（streak"冻结/归零二分 + 日期锚点快照" vs 基线的"或"字歧义带进代码）、时间类边界测试（5 组 vs **0 组**）、逻辑硬伤预防（"无后端却写留存率北极星"被参谋在草稿期拦下）。

**框架的新失败模式（同样重要）**：B2 代码出现 `parseInt` 静默取整违反自家 PRD、模板回滚只回内存不落盘、给不存在的旧版做迁移——**工件变多后契约精度向代码传导会衰减**，因此增加"契约↔代码逐条对齐"抽查门禁。

## 5. 模型路由实测 / Model routing (field notes)

- 契约 frontmatter 平 id（`deepseek-v4.1-flash`）→ 实测仍走套餐默认模型（客户端 `parseModelRef` 把平 id 归入默认供应商，找不到即静默回落）；
- 正确格式 `"<providerId>/<modelId>"`；
- 角色清单会话启动时加载：会话中途增改契约/新角色均不生效（新角色派发直接报 not found）；
- 验证以计费库 `model_usage.model_id` 为准（本仓库所有"实际模型"结论皆出自该表）。

## 6. 成本汇总 / Cost accounting

全部实验 ≈ **1.34M subagent tokens**（探针 96k + demo 355k + 对照实验 893k），10 余次编排全部遵守"并发 ≤3、参谋只读、等预算意识"的框架自身纪律。最大单笔浪费：一次派发引用了未落盘文件导致返修 agent 拒收重来（98k）——由此催生"派发前 pre-flight：所有被引用文件必须先落盘"规则。

## 7. 复现指南 / Reproduction

1. 准备同题任务书与评分卡（五维×5 分）；
2. 每条件独立派发 ≥2 遍，产出文件重命名脱敏（X1..Xn）；
3. 交独立评审 agent（不知道条件分组）按评分卡打分；
4. 对照时**等 token 预算**：基线组允许花同等 tokens（如多一轮自检），否则测到的是算力不是架构；
5. 实际模型验证：查客户端计费库 `model_usage.model_id`，不要信"声明"。
